ESP32 Library — User Manual

DualSense32 取扱説明書

DualSense PS5 DualShock 4 PS4

PlayStation のコントローラを ESP32 から使うためのライブラリです。名前は DualSense32 ですが、 DualShock 4（PS4）も同じように使えます。どちらのパッドも、あとで出てくる 3 つの繋ぎ方すべてで動きます。 ボタンもスティックもタッチパッドもジャイロも読めますし、 ライトバーの色、振動、それに DualSense ならアダプティブトリガ（引き金の手応え）も出せます。 この文書は ZIP を展開したところから、最初の 1 本が動き、自分のコードが 書けるようになるまでを順に説明します。

01

どれで繋ぐか決める

繋ぎ方が 3 通りあります。手持ちのボードで決まります。

1_Dongle
ESP32-S3 / S2

USB ポートに挿した Bluetooth ドングルが無線機になります。ESP32 内蔵の WiFi とは別系統です。

要: 標準 HCI ドングル（USB クラス E0/01/01）＋ USB-C → USB-A 変換
2_USBDirect
ESP32-S3 / S2

パッドをケーブルで直結します。ペアリングが要りません。

要: USB-C ケーブル（C to C）
3_BTClassic
初代 ESP32 のみ

ボード内蔵の Bluetooth で無線接続します。追加部品なしで一番手軽です。

要: なし
S3 に Bluetooth Classic が無い理由

ESP32-S3 / C3 / C6 / H2 には Bluetooth Classic の無線が載っていません（BLE のみ）。 どちらのパッドも Bluetooth Classic なので、S3 で無線を使うには外付けのドングルが要ります。 逆に初代 ESP32 には Classic がありますが、USB ホスト機能がないのでドングルは使えません。

どちらのコントローラか

どちらのパッドも 3 経路すべてで動きます。経路を決めるのは手持ちのボードで、 持っているコントローラではありません。

DualShock 4 の方が小ぶりです。アダプティブトリガが無く、マイクもミュートボタンも 無く、プレイヤー LED もありません。代わりに自分で点滅できるライトバーがあり、 タッチパッドは DualSense より縦が短くなっています。 一覧は 6-8、スケッチがどちらのパッド向けかを書き分ける方法は 第 5 章にあります。

2 台目のために読み直す章はありません。違いがあるところは、その機能の説明の中で その都度書いてあります。

実機で確認できていること

「対応」と書くと幅が広いので、確認できた範囲をそのまま書きます。

DualShock 4 は ESP32-S3 で、有線とドングルの両方を、 CUH-ZCT2 のパッドで動かしました。接続・入力・出力・再接続まで一巡しています。 加速度の大きさは 1.001 G、静止時のジャイロは 0.5 deg/s 以内に収まりました。 この 2 つの数字は、DualShock 4 用のオフセットを使い、かつパッドが名乗ったあとで キャリブレーションを読み直していなければ出ません。Bluetooth では キャリブレーションがデバイス判明より先に届くので、リンク側でバイト列を保持して 読み直しています。5_SelfTest > Ds4Core は実機で 162 件のプロトコル検証が通ります。

初代 ESP32 の経路（3_BTClassic）はコードは入っていますが、DualShock 4 での 実機確認はできていません。判別もデコードも他の経路と同じ仕組みで、まだ実物で 走らせていないだけです。壊れているのではなく、未確認です。

ボードの設定

ツールメニューでの設定です。繋ぎ方によって違います。

3-1　初代 ESP32（3_BTClassic）

項目値理由

Erase All Flash状況による3-3 を参照

Partition Scheme を忘れると text section exceeds available space で書き込めません。

3-2　ESP32-S3（1_Dongle / 2_USBDirect）

項目値理由
ボードESP32S3 Dev Module など実物に合わせて
Partition Scheme既定のままで入ります
USB CDC On BootEnabledシリアルモニタに何も出ないときはこれ
シリアルが 1 文字も出ない場合

ボードによっては USB CDC が既定で無効です（LOLIN S3 Mini など）。まずここを疑ってください。

3-3　Erase All Flash — 無線で繋ぐなら重要

ESP32 はペアリング情報をフラッシュに覚えます。この記憶を消すかどうかの設定です。

鍵は両側に残る

初めて繋ぐとき、または繋がらなくなったときは Enabled にしてください。 片方だけが古い鍵を覚えていると、以後ずっと認証で失敗し続けます。 その場合は ESP32 側は Erase All Flash、パッド側は CREATE + PS で、 両方に忘れさせるのが確実です。パッドはホストを 1 台しか覚えません。

3-4　ドングルの条件

項目条件
USB クラスE0/01/01。これが標準 HCI ドングルの印です
対応Bluetooth Classic（BR/EDR）。BLE 専用は不可
ファームウェア内蔵のもの。ホストから流し込んでから動く型は対象外です
電源・速度バスパワー 100 mA 程度、フルスピード
形状USB-A。S3 は USB-C なので変換が要ります

箱の Bluetooth 5.x / 6.0 という表記は関係ありません。 どちらのパッドも Classic なので、BLE 専用と書いてあるものだけ避けてください。

開発に使ったもの

UGREEN Bluetooth 6.0 アダプタ（EDR ＆ BLE、Windows 11 / 10 / 8.1 対応）。 Windows のデバイスマネージャには BARROT Bluetooth 6.0 Adapter と出ます。 ESP32-S3 から見えた値は次のとおりで、ファームウェアの転送なしで動きました。 

vid:pid        33FA:0012
device class   E0/01/01
product        UGREEN BT6.0 Adapter
speed          full
configuration: 2 interfaces, 100 mA

4_Troubleshooting > WhatIsOnUSB の出力です。挿したドングルがこう出れば当たりです。

3-5　ドングルはどこに挿すか

S3 の USB-C は 2 つあります。ドングルはネイティブ USB 側です。 もう一方は PC に挿したままにしてください。書き込みとシリアルモニタに加えて、 ドングルの電源もそこから来ます。

どちらがネイティブ USB か分からないボード

4_Troubleshooting > WhatIsOnUSB を書き込んで、 ドングルを挿し替えてください。ドングルの中身が出てくる方がネイティブ USB です。

04

最初の 1 本を動かす

ファイル > スケッチ例 > DualSense32 >（自分の繋ぎ方）> Basics を開きます。

4-1　書き込む

第 3 章のボード設定を済ませて書き込みます。シリアルモニタは 115200 bps です。

4-2　パッドを繋ぐ

有線（2_USBDirect）なら挿すだけです。ここから先は無線の話です。

  1. 1CREATE ボタンを押したままにします。タッチパッドの左上にある小さいボタンです。
  2. 2そのまま PS ボタンも押します。
  3. 3ライトバーが速く点滅したら指を離します。これがペアリングモードです。
  4. 4ESP32 が見つけて自分から繋ぎに行きます。待つだけです。
2 回目以降

ESP32 側の記憶が残っていれば、PS ボタンを押すだけで繋がります。

DualShock 4 では、このボタンの名前が SHARE です。手順は同じで、SHARE を 押したまま PS も押し、ライトバーが速く点滅したら離します。場所も同じで、 タッチパッドの左にある小さいボタンに、Sony が印刷している古い方の名前が 付いているだけです。

4-3　動いたかどうか

操作起きること
× ボタンを押しっぱなしライトバーが赤くなり、両方のモーターが回る
離す水色に戻り、振動が止まる

05

コードの読み方

Basics の中身です。これが全部で、他のサンプルはここに表示を足しただけです。

#include <DualSense32.h>

DualSense32 pad;                       // ① 用意する

void setup() {
  Serial.begin(115200);
  if (!pad.begin()) Serial.println("begin failed");   // ② 始める
}

void loop() {
  pad.update();                        // ③ 毎回これを呼び出す
  if (!pad.connected()) return;

  if (pad.pressed(DS_CROSS))  Serial.println("cross down");   // ④ 聞く
  if (pad.released(DS_CROSS)) Serial.println("cross up");

  if (pad.down(DS_CROSS)) {
    pad.lightbar(255, 0, 0);           // ⑤ 命じる
    pad.rumble(120, 120);
  } else {
    pad.lightbar(0, 160, 255);
    pad.rumble(0, 0);
  }
}

① 用意する — 繋ぎ方はここだけで決まる

DualSense32 pad;                       // 自動。初代 ESP32 なら内蔵無線、S3/S2 ならドングル
DualSense32 pad(ds_link_usb_hid());    // 有線（S3）  + #include <ds_link_usb_hid.h>

無引数がふつうの書き方です。#include <DualSense32.h> だけで済みます。 初代 ESP32 には Bluetooth Classic があって USB ホストが無く、S3 / S2 はその逆なので、 チップが決まれば無線の経路は 1 通りしかありません。ライブラリがそれを選びます。

明示が要るのは有線（S3）だけです。S3 ではドングルもパッドも同じ USB ポートに 挿さるので、どちらのつもりかはコンパイル時には分かりません。既定はドングルです。

経路を明示したいときは、いつでも書けます。

DualSense32 pad(ds_bt_bluedroid());    // 初代 ESP32  + #include <ds_bt_bluedroid.h>
DualSense32 pad(ds_link_usb_hci());    // ドングル    + #include <ds_link_usb_hci.h>

3 経路の違いはこの 1 行だけです。下のコードは 1 文字も変わりません。

② 始める

pad.begin();                        // 勝手に探す。ペアリングモードのパッドを見つける
pad.begin("AA:BB:CC:DD:EE:FF");     // このパッドだけに繋ぐ

近くに複数台あるとき以外は pad.begin() で十分です。アドレスの打ち間違いは false が返るのですぐ分かります。

アドレスは繋がってから聞けます。ペアリングして 1 回繋いだあと、

char who[18];
if (pad.address(who)) Serial.println(who);   // 24:A6:FA:23:12:64

pad.printEvents(Serial) を呼び出していれば、繋がった時点で link: connected 24:A6:FA:23:12:64 と 1 行出ます。3 経路とも同じです。

③ 毎回これを呼び出す

この 1 行を書き忘れると、ボタンを押しても反応せず、ライトバーの色も変わりません。 コントローラとのやり取りはここでしか行われないからです。エラーは出ません。

コントローラからのデータは裏で動いている通信タスクが受け取っています。 そのまま読むと「スティックは今のフレーム、ボタンは前のフレーム」という混ざった値になります。 update() はその瞬間をコピーするので、そのあと読んだ値は 全部同じ瞬間のものです。

④ 聞く／⑤ 命じる

出力は設定するだけです。send() を書く必要はありません。update() が送ります。

どちらのパッド向けか — 書き方は 2 通り

ここまでの内容は DualSense でも DualShock 4 でも同じです。同じでないのは ハードウェアの方で、DualShock 4 にはアダプティブトリガもマイクもプレイヤー LED もありません。それをどう扱うかはスケッチ側で決めることになり、答えが 2 つ あります。どちらかを意識して選んでください。失敗の出方が全く違います。

DualSense32 + supports()#include <DualShock4.h>
決まるタイミング動いている最中コンパイルするとき
受け入れるパッド挿さった方1 種類だけ
無い機能を叩いたときfalse が返り、数えられ、報告されるビルドが通らない

1 つのバイナリで両方受ける

DualSense32 のまま、書き方も変えずに、パッド側に何があるかを聞きます。

if (pad.supports(DS_CAP_ADAPTIVE_TRIGGERS)) pad.triggerRight(block);
if (pad.supports(DS_CAP_PLAYER_LEDS))       pad.playerLeds(10101);

「どのパッドか」ではなく「何が要るか」で聞くのがこつです。supports() は ハードウェアの能力を答えるので、このライブラリより新しいパッドが来ても 書いたコードはそのまま通ります。フラグの一覧は 6-8。

無いかもしれないハードウェアを触る設定関数は bool を返し、拒否されたときは 何も変わりません。見落とさないよう回数も数えています（7-5）。

パッドを型で名指しする

#include <DualShock4.h>
#include <ds_link_usb_hid.h>

DualShock4 pad(ds_link_usb_hid());

DualShock4 は、同じクラスから無いハードウェアを取り除いた型です。 黙って失敗させる代わりに、拒否されるはずだった呼び出しがそもそもビルドを 通りません。エラーはその行を名指しします。 

error: use of deleted function 'bool DualShock4::triggerRight(...)'
error: use of deleted function 'bool DualShock4::micLed(uint8_t)'
error: use of deleted function 'bool DualShock4::playerLeds(...)'

ボタンはふつう DSButton の共通名（DS_CROSS、DS_CREATE など）で 書けます。Sony が印刷した名前で書きたいときだけ、DS4_SHARE などの DS4Button 別名も使えます。DS4_MUTE はそもそも存在しません。 マイクが無く、そのためのボタンも無いからです。ミュートボタンを取りに行っても、 永久に false を返す呼び出しにはならず、こうなります。 

error: 'DS4_MUTE' was not declared in this scope

DS5_CROSS と書くと落ちます。共通の綴りは DS_CROSS です。 DualSense 専用の別名で書いているということは別のパッド向けに書かれたスケッチという 合図なので、まだ安いうちに捕まえます。

なぜ #define ではこの仕事ができないのか

Arduino のビルドは、ライブラリの .cpp を .ino とは別々に コンパイルします。スケッチ側で定義したマクロはそこまで届かないので、 ライブラリの中身を変えることはできません。その境界を越えられるのは型だけです。 スイッチではなくクラスになっているのはそのためです。

実行時のチェックが 1 つだけ残ります。残さざるを得ません。USB ポートには 「これから何が挿さるか」を前もって聞けないからです。そのため connected() は 本物の DualShock 4 が繋がったときだけ true になり、代わりに DualSense が来た ときは mismatched() が true になります。 

void loop() {
  pad.update();
  if (pad.mismatched()) return;      // DualSense が来た。スケッチ違い
  if (!pad.connected()) return;

  if (pad.pressed(DS_CREATE)) Serial.println("share");
}

このチェックが無いと、DualSense のレポートを DualShock 4 のものとしてデコード します。落ちもせず、エラーも出ず、ただボタンが一生反応しないスケッチになります。

DualSense32 で書いている限り、この名前はどちらのパッドでもそのまま使えます。 DualShock4 型で書いた場合（第 5 章）も DS_CROSS などの 共通名をそのまま使えます。印刷名を優先したいときだけ DS4_SHARE などの別名を使います。

DualSenseDualShock 4
タッチパッドの左の小さいボタンDS_CREATEDS_CREATE

DualShock 4 を DualSense32 経由で読むと、pad.down(DS5_MUTE) は常に false です。パッドが黙っているのではなく、ミュートボタンが無く、その位置のビットが レポートカウンタだからです。ボタンとしてデコードすると、勝手に点滅するミュートに なります。この読み出しも拒否として数えられます（7-5）。

6-2　down / pressed / released

pressed() を使うべきところに down() を書くと、押している間ずっと 処理が走ります。1 回のつもりが毎秒数百回になります。 

// 押している間モーターを回す → down
if (pad.down(DS_R1)) motorOn(); else motorOff();

// 押すたびに 1 発だけ撃つ → pressed
if (pad.pressed(DS_R1)) fire();

// ここで down を書くと、押している間ずっと撃ち続けます（毎秒数百発）

6-3　スティック

int x  = pad.leftX();    // -128 〜 127、中央が 0
int y  = pad.leftY();
int rx = pad.rightX();
int ry = pad.rightY();

pad.deadzone(8);         // ±8 以内は 0 とみなす（既定 8）
pad.deadzone(0);         // 無効化。生の値が見たいとき

6-4　トリガ

L2 / R2 は押し込み具合と底まで引いたクリックの 2 つが取れます。

uint8_t r    = pad.r2();                  // 0〜255 のアナログ値
bool clicked = pad.down(DS_R2_CLICK);    // 底まで引いた

analogWrite(motorPin, pad.r2());          // アクセルそのもの

DualShock 4 でも読み方は全く同じです。こちらのトリガはただのバネなので、 無いのは引くときの手応えの方です（7-3）。

6-5　タッチパッド

raw() から取ります。2 本まで同時に追えます。

const ds_state_t &s = pad.raw();

if (s.has_touch && s.touch[0].active) {
  Serial.printf("指1 %u,%u (id %u)\n",
                s.touch[0].x, s.touch[0].y, s.touch[0].id);
}

DualShock 4 のタッチパッドは幅が同じで、縦が短い 1920 x 942 です。 幅は同じなので x はそのまま、y だけ実物に合わせてください。1080 のつもりで 扱うと、下端に触れた指が 8 分の 7 くらいの位置として読めます。

id は指を置くたびに増える番号です。滑らせている間は変わらないので、 「同じ指の動きか、置き直したか」を id で判別できます。

どうやって見分けているか

有線では USB のプロダクト ID から。どちらのパッドも入力レポートは 0x01 の 64 バイトなので、レポートそのものでは区別が付きません。 ディスクリプタのプロダクト ID なら区別できます。

プロダクト IDパッド
0x05C4DualShock 4、CUH-ZCT1
0x09CCDualShock 4、CUH-ZCT2
0x0BA0DualShock 4 の USB アダプタ

Bluetooth ではレポート ID から。向こうにはプロダクト ID がありません。 0x31 が DualSense、0x11 が DualShock 4 です。フィーチャレポートを要求する までどちらのパッドも送ってくる 0x01 は何も名乗っていないので、 推測材料には使いません。ここで推測すると、接続のたびに 1 フレーム目で パッドをランダムに選ぶことになります。0x01 のレイアウトは両者同じなので、 判明していない間も正しくデコードできています。

判明するまでの間を埋める — begin() に想定を渡す

判明していない間、困るのは出力だけです。DualSense と DualShock 4 では 出力レポートの形式そのものが違うので、どちらか決まらないと組み立てられません。 そこで begin() に想定を伝えられます。 

pad.begin(DS_DEVICE_DUALSHOCK4);                        // 想定を伝える
pad.begin(DS_DEVICE_DUALSHOCK4, "AA:BB:CC:DD:EE:FF");   // 想定 ＋ MAC

DualShock4 型なら型が言っているので書く必要はありません。 pad.begin() も pad.begin("AA:BB:...") も、そのまま DualShock 4 想定で始まります。

伝えなかった場合、判明するまでの出力は保留されます。捨てられはしないので、 lightbar() などの設定はパッドが名乗った直後に届きます。数フレーム遅れるだけです。

想定はリンクが本当に判別したら必ず負けます。違っていれば device() がそう言い、DualShock4::mismatched() が真になります。

答えそのものを固定する — クローン向け

クローンや、このコードより新しい版のために、答えを上書きすることも できます。こちらは想定と違い、プロダクト ID より強い。 

ds_link_usb_hid_force_device(DS_DEVICE_DUALSHOCK4);   // begin() の前に

普通は要りません。ログにはパッドが繋がったと出ているのに、スティックから先の 値が全部でたらめ、というときに使ってください。

7-4　ライトバーの点滅 — DualShock 4 のみ

DualShock 4 は自分でライトバーを点滅させられます。リズムはパッドが刻むので、 警告灯を出しっぱなしにしてもスケッチ側の手間は増えません。 

pad.lightbar(255, 0, 0);       // 色はこれまでどおり設定する
pad.lightbarBlink(50, 50);     // 0.5 秒点いて 0.5 秒消える
pad.lightbarBlink(200, 1);     // 点灯に見えます。2 秒点灯・10 ms 消灯

消灯時間に 0 を渡してはいけません。パッドは新しい色も新しい速さも 点滅の境界でしか受け付けません。消灯 0 は境界そのものを無くすので、 ライトバーはそれまでの表示を保ったまま、後から送ったものを無視し続けます。 lightbarBlink(0, 0) はさらに悪く、消灯します。 どちらも「点灯」ではありません。

点灯に見せたいときは、長い点灯時間と消灯 1 を使って ください。DS4 の実機で確認: 消灯 10 ms は見えず、20 ms は見えます。消灯 1 なら1レポートで色も速さも一度で変わります。

単位はどちらも 10 ms なので、50 で 500 ms です。点灯時間と消灯時間なので、 揃える必要はありません。

DualSense にこの機能は無く、false が返ります。両方のパッドで点滅させたいなら、 millis() と lightbar() で自分の loop で作ることになります。

8-1　ラジコン（スティックでモーター）

#include <DualSense32.h>
DualSense32 pad;

const int PWM_L = 25, PWM_R = 26;

void setup() {
  Serial.begin(115200);
  pinMode(PWM_L, OUTPUT);
  pinMode(PWM_R, OUTPUT);
  pad.begin();
  pad.deadzone(12);          // 手を離したら確実に止める
}

void loop() {
  pad.update();

  // ★ 繋がっていないときは必ず止める
  if (!pad.connected()) {
    analogWrite(PWM_L, 0);
    analogWrite(PWM_R, 0);
    return;
  }

  int fwd  = -pad.leftY();   // 上に倒すとマイナスなので反転
  int turn =  pad.rightX();

  int l = constrain(fwd + turn, -128, 127);
  int r = constrain(fwd - turn, -128, 127);

  analogWrite(PWM_L, abs(l) * 2);
  analogWrite(PWM_R, abs(r) * 2);
}

電波が切れても、最後に読んだ値はそのまま残ります。connected() を見ずに leftY() だけで動かしていると、切れた瞬間の速度でモーターが回り続けます。 繋がっていない間は出力を 0 にしてください。

これは症状が「ペアリングできないコントローラ」と見分けが付かないので、 節を分けて書きます。パッドはペアリングモードで点滅し、ESP32 は何も言わず、 思い付く対処は全部あさっての方を向いています。

ボンドが保存されていると、リンクはインクワイアリスキャンを意図的に止めます。 ホストを覚えているパッドは PS を押すと自分からホストをページしてくるので、 同時にスキャンを走らせると、そのページに応答できなくなるからです。だから待つ 方が正しい — そのパッドについては。まだペアリングしていない別のパッドは、 走らないままのスキャンでしか見つけられません。

なので、先に古いボンドを消します。

ds_link_usb_hci_clear_bond(pad.transport());

そのあとボードをリセットしてください。ボンドは NVS にあるので、 Erase All Flash Before Sketch Upload = Enabled でも同じことができます （大雑把ですが。3-3）。
